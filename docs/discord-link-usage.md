# 디스코드 링크 저장 사용 안내

확인일: 2026-09-10. 저장소 코드와 로컬 Hermes 설정을 확인한 안내다.
운영 프로세스의 유효 설정, 실제 누락 메시지와 DB 기록은 대조하지 않았다.

## 지금 사용하는 방법

- 한 메시지에 URL을 한 줄씩, 최대 5개까지 넣는다.
- 봇의 결과 답변에서 각 URL의 저장 성공·중복·실패를 확인한 뒤 다음 묶음을 보낸다.
- 하나씩 보낼 때도 결과 답변을 받은 뒤 다음 URL을 보낸다.
- 6개 이상이면 5개 이하로 나눈다. 현재 에이전트 지침은 앞의 최대 5개만 처리한다.
- 기존 메시지 편집으로 URL을 추가하지 않는다. 현재 지침은 새 텍스트 메시지만 처리한다.
- 속도 제한 안내가 오면 안내된 재시도 시각까지 기다린다. 한 메시지에 모아도 URL별 호출이므로 제한을 우회하지 않는다.

예시:

```text
https://example.com/tool-a
https://example.org/tool-b
https://example.net/tool-c
```

## 확인한 근거와 한계

- `scripts/discord-favorite-mcp.ts`: 메시지마다 카테고리를 새로 읽고 URL마다 저장 도구를 호출하며 최대 5개를 처리하도록 안내한다.
- `.kiro/specs/discord-link-auto-ingest/requirements.md`: 최대 5개, 중복 URL 제거, 메시지 ID 보존, 연속 메시지 합치기 금지 계약을 정의한다.
- `supabase/migrations/0006_discord_link_auto_ingest.sql`: 최근 600초의 전역 호출 기록을 기준으로 30회 제한을 적용한다. 실제 운영 DB 적용 상태는 이번에 확인하지 않았다.
- 로컬 Favorite 프로필의 채널 지침도 최대 5개이며 편집·첨부·임베드를 제외한다.
- 로컬 공통 Hermes 설정의 `display.busy_input_mode`는 `interrupt`이고 Favorite 프로필에는 명시적 재정의가 없다. 설치된 gateway 코드도 기본값을 `interrupt`로 둔다. 따라서 처리 중 연속 입력의 간섭을 조사할 이유가 있지만, 실행 중 환경 변수·프로필 상속·로그를 확인하지 않았으므로 실제 누락 원인으로 확정하지 않는다.

## 더 편하게 쓰기 위한 개선 방향

여러 메시지를 연속으로 보내도 메시지 ID별로 접수하고 순서대로 끝까지 처리하는 방식이 적합하다.
우선 Favorite 전용 대기열 설정과 메시지 ID 보존을 검증하고, 단순 텍스트 병합으로 여러 메시지를 한 턴으로 합치지 않아야 한다.
장기적으로는 접수 기록을 영속 저장하고 실패 재시도와 메시지별 접수·완료 표시를 제공하면 재시작 후에도 미처리 항목을 복구할 수 있다.

### 권장 변경 순서 — 제안, 미적용

1. **Favorite 전용 순차 처리**: 프로필에 `display.busy_input_mode: queue`를 명시하는 것을 출발점으로 삼되, Discord 수신부터 실행까지 원본 메시지 이벤트를 각각 FIFO에 보존한다. 다른 프로필의 공통 설정은 변경 대상에 포함하지 않는다.
2. **텍스트 병합 제거**: Favorite의 처리 중 입력과 에이전트 시작 직전 입력 모두 메시지별 독립 작업으로 연결한다. 현재 설치된 Hermes의 `gateway/run.py`에는 FIFO 함수가 있지만, 일반 텍스트 queue 분기는 busy handler에서 `False`를 반환하며 `gateway/platforms/base.py`의 텍스트 병합 경로로 넘어갈 수 있다. 따라서 queue 설정과 batching 비활성화만으로 메시지 분리가 보장된다고 판단하지 않는다. 지원되는 프로필별 확장 지점을 먼저 확인하고, 없으면 별도 수신 어댑터 또는 범위를 제한한 gateway 변경을 검토한다.
3. **접수와 완료 구분**: 메시지별로 접수 표시와 `저장 3 · 중복 1 · 실패 1` 같은 결과를 제공한다. 대기열 한도 초과는 명시적으로 알린다. 접수 기록이 메모리에만 있으면 재시작 복구까지 보장하는 문구는 쓰지 않는다.
4. **영속 접수와 복구**: 수신 메시지 및 URL별 처리 상태를 저장하고 재시작 후 미완료 항목을 재개한다. 기존 저장 API의 중복 방지와 결과 코드 계약을 유지하며, 일시 오류는 기존 재시도 규칙 안에서 처리하고 속도 제한은 `retryAt` 이후 처리한다. 영구 실패는 이유와 사용자 조치를 표시한다.

1~2를 먼저 검증해 연속 입력 간섭을 줄이고, 재시작을 포함한 누락 방지까지 필요하면 3~4를 함께 구현한다.
메시지당 최대 5개는 우선 유지하되, 초과분을 조용히 버리지 않고 별도 메시지로 보내도록 안내하는 동작을 추가한다.

### 적용 완료 판단 기준

- 작업 중 링크 메시지 10개를 연속 수신해 원본 메시지 ID 10개와 URL별 최종 결과가 모두 대응한다.
- 에이전트 시작 직전의 연속 입력에도 덮어쓰기·병합·중복 저장이 없다.
- 한 메시지의 5개 URL을 각각 처리하고, 6번째 이후에는 미처리 안내를 제공한다.
- 일시 오류·속도 제한·대기열 한도 초과를 조용히 누락하지 않는다.
- 영속 접수를 구현한 경우, 처리 중 재시작 후 미완료 작업이 복구되고 완료 항목이 중복 저장되지 않는다.
- 위 항목은 먼저 가짜 Discord 이벤트와 저장 API로 확인한다. 실제 Discord 수신 및 운영 DB 대조는 별도 검증이며, 현재 완료 증거는 없다.

이 문서는 사용 안내와 조사 결과만 기록한다. 봇 설정 변경, 재시작, DB 변경, Discord 메시지 전송은 수행하지 않았다.
