# 바이브코딩 GitHub 저장소 분류·등록 계획

> 상태: **구현 대기**
>
> 기준일: 2026-08-31 (Asia/Seoul)
>
> 범위: 정보구조, 기존 GitHub 링크 재분류, 승인된 신규 저장소 등록, 운영 검증

## 1. 결론

새 상위 카테고리를 만들지 않고 **`AI 도구 모음 > 바이브코딩`** 하위 카테고리를 만든다.

- 사용자는 링크의 호스팅 장소(`GitHub`)보다 사용 목적(`바이브코딩`)으로 찾는다.
- 새 하위 카테고리는 데스크톱 사이드바와 `AI 도구 모음` 목록의 하위 탭에 자동으로 나타난다.
- 모바일 상위 칩은 늘어나지 않아 현재 탐색 밀도를 유지한다.
- 같은 상위 안에서 이동하므로 기존 즐겨찾기 링크는 계속 홈의 `AI 서비스` 묶음에 남는다.
- 현재 관리자 화면이 카테고리 생성, 링크 등록, 링크 이동을 이미 지원하므로 1차 범위에는 UI 코드
  변경이 필요 없다.

카테고리 이름은 짧은 **`바이브코딩`**을 기본안으로 한다. `GitHub 저장소`는 링크들의 공통 속성이므로
카테고리명에 반복하지 않고, 주소와 설명에서 드러나게 한다.

## 2. 현재 상태

2026-08-31 운영 Supabase를 읽기 전용으로 조회한 결과는 다음과 같다.

- 전체 링크: 487개
- `github.com` 링크: 12개
- GitHub 링크 12개 전부: `AI 도구 모음 > 오픈소스·자료 모음`
- 운영 migration: 로컬과 원격 모두 `0001`~`0013` 일치
- 운영 데이터의 `AI 도구 모음`에는 이미 `코딩·에이전트`, `오픈소스·자료 모음`, `프롬프트·디렉터리`
  등 인접 하위 분류가 있다.

`docs/data/links.json`은 초기 시드 원본이고 README가 `docs/`를 읽기 전용 핸드오프로 규정한다. 현재
운영 데이터도 초기 시드와 달라졌으므로 이번 작업에서 이 파일을 운영 진실로 갱신하거나 `npm run seed`를
실행하지 않는다. 운영 변경은 새 migration과 관리자 화면을 기준으로 한다.

## 3. 분류 기준

### 포함

아래 중 하나를 직접 제공하는 공개 GitHub 저장소를 넣는다.

- 코딩 에이전트와 에이전트 작업 흐름
- 스킬, 규칙, 프롬프트, 컨텍스트 팩
- 앱·웹 제작용 템플릿과 스캐폴딩
- 디자인에서 구현으로 이어지는 도구와 디자인 컨텍스트
- 코딩 에이전트의 평가, 디버깅, 관찰, 토큰·도구 출력 최적화
- 기획부터 출시까지 AI와 함께 제품을 만드는 실행 자료

### 제외 또는 다른 분류 유지

- GitHub에 있다는 사실만 공통이고 바이브코딩 사용 장면이 불명확한 저장소
- 일반 AI 비서, 이미지 프롬프트 모음, 스크래핑 비교처럼 기존 분류가 더 정확한 자료
- 저장소가 아닌 개인 프로필, issue, release 한 건, 일시적인 검색 결과
- 접속할 수 없거나 보관 처리돼 실제 사용 경로가 불명확한 저장소

### 링크 작성 규칙

- URL은 원칙적으로 `https://github.com/<owner>/<repository>` 저장소 루트를 쓴다.
- 특정 하위 디렉터리 자체가 자료의 핵심일 때만 `/tree/...` 경로를 유지한다.
- 제목은 저장소명만 쓰고, 동명 충돌이 있을 때만 `owner/repository`를 쓴다.
- 설명은 “무엇이며 언제 도움이 되는지”를 한국어 한 문장, 200자 이하로 쓴다.
- 현재 관리자 화면은 tags를 편집하지 않으므로 이번 분류를 tags에 의존시키지 않는다.
- DB의 `normalized_url` unique 제약을 최종 중복 경계로 사용한다.

## 5. 구현 단계

### 단계 0 — 승인 목록 확정

1. 카테고리 이름 `바이브코딩`을 확정한다.
2. 위 기존 링크의 `이동/유지/검토`를 확정한다.
3. 신규 저장소마다 URL, 표시 이름, 한 줄 설명, 사용 장면을 한 행으로 정리한다.
4. 저장소 루트가 아닌 URL은 정확한 하위 경로를 유지할 이유를 확인한다.

완료 기준: 기존 이동 목록과 신규 등록 목록의 URL이 중복 없이 고정된다.

### 단계 1 — 운영 사전 점검

읽기 전용 SQL로 다음을 확인한다.

1. 상위 `AI 도구 모음`이 정확히 1개다.
2. 같은 상위 아래 `바이브코딩`이 없거나, 있으면 기대한 leaf 카테고리다.
3. 이동 대상 URL이 각각 정확히 1개이고 현재 `오픈소스·자료 모음`에 있다.
4. 신규 URL의 `normalized_url` 충돌이 0개다.
5. 이동 대상의 `id`, `is_favorite`, `fav_order`, 클릭 합계, favicon, source를 복구 증거로 기록한다.
6. 적용 직전 운영 DB backup 또는 복구 지점을 만든다.

한 항목이라도 기대와 다르면 자동 보정하지 않고 대상 목록을 다시 승인받는다.

### 단계 2 — 재실행 안전 migration 작성

`supabase/migrations/0014_add_vibe_coding_repositories.sql` 한 파일에서 다음을 transaction으로 처리한다.

1. `AI 도구 모음` 아래에 `바이브코딩` leaf를 만든다.
2. 탐색 순서는 `코딩·에이전트` 다음이 되도록 뒤 하위 분류의 `sort_order`를 한 칸 민다.
3. 승인된 기존 URL만 `normalized_url`로 찾아 새 카테고리로 이동한다.
4. 이동 시 `category_id`와 새 카테고리 안의 `sort_order`만 바꾸고 bookmark `id`, URL, 제목, 설명,
   favicon, source, `is_favorite`, `fav_order`는 보존한다.
5. 승인된 신규 저장소만 `source = 'manual'`, `is_pinned = false`로 등록한다. 충돌 시 기존 행을
   덮어쓰지 않고 migration을 중단한다.
6. 대상 수, 최종 카테고리, 중복 0건을 SQL 마지막에서 다시 검증한다.

클릭은 bookmark ID를 참조하므로 기존 행을 삭제 후 재삽입하지 않는다. 이 원칙이 클릭 이력과
즐겨찾기 상태를 보존한다.

### 단계 3 — 로컬·격리 검증

1. 깨끗한 로컬 또는 일회용 Supabase에서 `0001`~`0014` migration을 순서대로 적용한다.
2. 사전 상태 fixture에 migration을 한 번 적용하고, 다시 실행해도 중복 카테고리·링크가 생기지 않는지
   확인한다.
3. 잘못된 부모, 누락된 기존 URL, 신규 URL 충돌 fixture에서 전체 transaction이 실패하는지 확인한다.
4. 앱 코드 변경이 없더라도 데이터 모양 회귀를 확인하기 위해 테스트, 타입 검사, lint, build를 실행한다.

예정 명령:

```bash
npx supabase db reset
npm test
npm run typecheck
npm run lint
npm run build
```

`npx supabase db reset`은 로컬/일회용 프로젝트에서만 실행하고 linked 운영 DB에는 실행하지 않는다.

### 단계 4 — 운영 반영

1. migration commit을 먼저 push하고 최종 SHA를 기록한다.
2. 단계 1의 read-only preflight를 같은 승인 목록으로 다시 실행한다.
3. 명시적인 운영 적용 승인 뒤 `npx supabase db push --linked`로 `0014`만 적용한다.
4. `supabase migration list --linked`에서 로컬/원격 `0014` 일치를 확인한다.

앱은 매 요청마다 공개 데이터를 읽으므로 데이터-only 변경에는 별도 Vercel 배포가 필요하지 않다. 앱 코드나
화면 문구를 함께 바꾸게 되면 그때는 별도 배포와 `/api/version` SHA 검증을 추가한다.

### 단계 5 — 실제 화면 검증

1. 데스크톱 사이드바에서 `AI 도구 모음`을 펼쳤을 때 `바이브코딩`과 정확한 개수가 보인다.
2. `AI 도구 모음` 페이지에 `바이브코딩` 탭이 나타나고 선택 시 승인된 링크만 보인다.
3. 모바일에서는 불필요한 상위 칩이 늘지 않고 `AI 도구 모음` 진입 뒤 같은 탭을 사용할 수 있다.
4. 기존 즐겨찾기 링크는 홈의 `AI 서비스` 묶음과 `/favorites`에서 그대로 보인다.
5. 관리자 화면에서 새 카테고리 선택, 신규 링크 추가, 기존 링크 이동이 가능하다.
6. 기존 이동 링크의 클릭 합계, favicon, 즐겨찾기 여부가 사전 기록과 같다.
7. `오픈소스·자료 모음`에는 유지하기로 한 자료만 남고 상위 `AI 도구 모음` 총 링크 수는
   “이동 전 수 + 신규 등록 수”와 같다.

## 6. 수용 기준

- `AI 도구 모음` 아래 `바이브코딩` leaf가 정확히 1개다.
- 승인된 기존 저장소만 이동하고 승인된 신규 저장소만 추가된다.
- 전체 `normalized_url` 중복은 0건이다.
- 기존 bookmark ID, 클릭 이력, favicon, source, 즐겨찾기 상태와 순서는 보존된다.
- 데스크톱, 모바일, 관리자 화면에서 별도 코드 분기 없이 새 분류를 사용할 수 있다.
- 운영 migration history가 로컬과 일치하고 실제 화면 결과까지 확인된다.

## 7. 복구 계획

- 적용 전 backup/복구 지점과 이동 대상의 원래 `category_id`, `sort_order`를 보관한다.
- 문제가 생기면 신규 행만 exact normalized URL 목록으로 삭제하고, 기존 행은 기록한 ID 기준으로 원래
  카테고리와 순서에 되돌린다.
- `바이브코딩`이 비었는지 확인한 뒤에만 카테고리를 삭제한다.
- rollback SQL도 기대 행 수가 다르면 중단하도록 작성하며, 범용 조건이나 전체 삭제를 사용하지 않는다.

## 8. 후속 범위

저장소 수가 늘어 검색성이 다시 나빠질 때만 다음을 별도 Story로 검토한다.

- 관리자 tags 편집과 `에이전트`, `스킬`, `디자인`, `템플릿`, `디버깅` 필터
- GitHub API 기반 archived 여부·최종 활동 시점 점검
- 주기적인 dead-link/redirect 검사

이 기능들은 이번 “별도 카테고리 생성과 링크 등록”의 완료 조건에는 포함하지 않는다.
